# Component: lecturer

`POST /api/lecturer` saves an owned course’s mastery threshold between 0.5 and 0.99. The Supabase function locks the course row and writes the change and history entry in the same transaction. History records the previous and new values, lecturer and time. Once the write lands the route's `recalculate` recomputes stored mastery for every student enrolled in that course, because whether a module is mastered is now judged against a different mark (ADRs 0005 and 0008); a change that saves nothing still recomputes, which is harmless and keeps the stored copy from going stale.

> [C4 index](../../README.md) / Level 3: Components / Turn and admin server

`GET /api/lecturer` verifies the Supabase session and passes its email to `handleLecturer`. The handler checks the lecturer allowlist and returns 401 for a missing session or 403 for an email outside the list. The landing check does not use this route: `GET /api/staff-role` (`server/staff/staff-role.ts`, reusing the lecturer and product-owner allowlist checks) answers `{productOwner, lecturer}` with 200 for anyone, a student included.

The handler reads through `LecturerStore`. The Supabase adapter selects course IDs and titles by owner email, counts enrollments in Postgres and reads course history with the server key. The page receives the count, history, title and ID for each owned course.

Both handlers take one optional collaborator besides the store: `recalculate`, a `MasteryRecalculator` from [`student-model`](05-student-model.md). A change to the course is a change to what every enrolled student's stored mastery means, so the handler calls `recalculate.forCourse(courseId)` after the write (ADR 0008). It is optional, so the tests of the answer alone need no database, and `stored-mastery-lecturer.test.ts` is where the recompute is pinned.

The course also carries its enrolled students: display name, student number, campus, email and enrollment date. `GET /api/lecturer?campus=` narrows each course's students to one campus (the enrolled count stays that of the whole class). The Supabase adapter reads the course's enrollments and resolves each student through the `student_directory` view, which joins the student profile to the account email. It never reads code, conversations, mastery or activity, and staff have no student number so they never appear.

The migration assigns the seeded Python course to the demo lecturer, records its first history entry, backfills enrollments and adds a trigger for new students. Supabase grants access to both tables to the server role. The handler tests use the memory store.

`GET /api/lecturer/spec` downloads the owned Python course's published JSON spec. `?draft=1` returns the course draft (or `null`), and `?draft=1&download=1` downloads it as a file (404 when there is none). `POST /api/lecturer/spec` with a course spec JSON saves it as the course draft and does not change what students see. Publish sends that draft through `import_course_spec`, which validates it and records one course history entry, then clears the draft; publishing with no draft is a 400 and writes no history. After a publish the route's `recalculate` recomputes stored mastery for every enrolled student (ADR 0008): the new spec may add, drop or move modules, exercises and questions, and evidence about content the course no longer has stops counting. Both routes build that recalculator once with `createSupabaseMasteryRecalculator`, which reads the published course, the enrollment list and the evidence with the server key, and opens the evidence and mastery stores of whichever course it is asked to recompute. `POST` with `{event: 'save', spec}` saves the editor's draft through the same validation, and `{event: 'discard'}` clears it. Every action returns 401 without a session and 403 for an email outside the lecturer allowlist, before the store is touched. The `draft` column of `courses` is, like `spec`, not readable or writable by `anon` or `authenticated` (courses boundary test). `?preview=1` returns the draft as a student would see it, with teacher-only fields marked and each exercise's tests included so the browser can run them, and it only reads: no draft change, no history entry and no student row. The download is private to the owning lecturer and includes the hints, quiz answers and reference solutions.

The sign-in code handler (`server/auth/handle-sign-in-code.ts`, `POST /api/sign-in-code`) is not part of this component: it only checks the address against `shared/student-email` and asks Supabase Auth to send a code.
